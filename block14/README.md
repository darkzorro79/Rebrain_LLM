# Блок 14: MCP (Model Context Protocol)

Материалы к уроку [«MCP (Model Context Protocol)»](https://my.rebrainme.com/course/llm/task/3155) (REBRAIN).

---

## Практическое задание

### Ресурсы

Вам предоставлена виртуальная машина с Ubuntu 24.04 с правами root и установленным python. А также — выделенный git репозиторий, куда будет необходимо загрузить ответ на задание.

### Задача

Реализуйте MCP сервер (`server.py`), который предоставляет функцию проверки состояния системного сервиса (через `systemctl status`). А также реализуйте клиента, который в бесконечном цикле будет принимать вопросы пользователя и отвечать на них, используя готовый MCP сервер.

Конечно. Чтобы задание по MCP (Model Context Protocol) было выполнимым и проверяемым, важно уточнить стек технологий (например, использование MCP SDK для Python) и чётко разделить роли сервера и клиента.

### Требования к реализации

**Архитектура MCP:**

- **Сервер (`server.py`):** должен использовать библиотеку **fastmcp** (Python SDK). Необходимо реализовать инструмент (tool) — **`check_service_status`**, который принимает имя сервиса и возвращает вывод команды `systemctl status <service_name>`.
- **Клиент (`client.py`):** должен инициализировать сессию с сервером (**через HTTP**), принимать запросы от пользователя и отправлять их в LLM с предложением утилит из MCP сервера.

**Интеграция с LLM:**

- Клиент должен использовать модель **`gemini-2.5-flash`** для обработки естественного языка.
- **Логика работы:** пользователь вводит запрос → клиент передаёт его в LLM → LLM решает вызвать tool на MCP-сервере → клиент выполняет вызов и передаёт результат обратно в LLM → LLM формирует итоговый ответ.

**Интерфейс:** бесконечный цикл ввода в `client.py` с обработкой команды **`exit`** для корректного завершения сессии и остановки сервера.

### Критерии успешного выполнения

- В Git-репозитории присутствуют файлы **`server.py`** и **`client.py`**.
- **Соблюдение протокола:** взаимодействие между компонентами реализовано строго через стандартные механизмы MCP (инструменты/tools), а не прямым вызовом `subprocess` внутри клиентского кода.

## Решение в этой папке

Ниже — как устроены файлы блока и как они соотносятся с заданием.

### `practic/server.py` — сервер под формулировку задания

- **FastMCP**, имя сервера `systemctl-service-checker`.
- Инструмент **`check_service_status(service_name: str)`** вызывает `systemctl status` через `subprocess.run` с таймаутом; в ответе объединяются stdout и stderr; обрабатываются таймаут, отсутствие `systemctl` и прочие ошибки.
- Точка входа: `mcp.run()` (транспорт по умолчанию в fastmcp — удобно для запуска как подпроцесса со стороны stdio-клиента).

### `practic/client.py` — интерактивный клиент с LLM и MCP tools

- Подключение к MCP **через stdio**: поднимается сессия `mcp` к локальному `server.py` (параметры `StdioServerParameters` с указанием интерпретатора Python и скрипта).
- **Важно:** в коде задан абсолютный путь к интерпретатору в виртуальном окружении (`.../block14/.venv/bin/python`). На другой машине его нужно заменить на актуальный `python` или путь к venv.
- LLM: OpenAI-совместимый клиент с `base_url` **`https://llm.rebrainme.study/`**, модель **`gemini-2.5-flash`**, ключ из переменной окружения **`API_KEY`**.
- Список tools запрашивается у MCP (`list_tools`), конвертируется в формат function-calling API; при ответе модели с `tool_calls` вызывается **`session.call_tool`**, результат с ролью `tool` уходит обратно в модель для финального ответа.
- **Интерфейс:** бесконечный цикл `input()`, выход по **`exit`** и по `KeyboardInterrupt`; при завершении вызывается отключение от сервера (закрытие stdio-сессии).

**Замечание по требованию «через HTTP»:** в эталоне в `practic/` клиент использует **stdio-транспорт MCP**, а не HTTP. HTTP-вариант см. в корне репозитория блока (ниже).

### `practic/user-repo-wiyqm/` — копия `server.py` / `client.py`

Дублирует логику из `practic/` для отдельного пользовательского репозитория (удобно как шаблон сдачи).

### Корневые `server.py` и `client.py` — демонстрация HTTP и другого набора tools

- **`server.py`:** FastMCP с ресурсом `system://logs`, промптом `analyze_incident` и инструментом **`execute_shell_command`** (общая shell-команда с простым чёрным списком опасных подстрок). Это **не** минимальная реализация `check_service_status` из задания.
- **`client.py`:** **`fastmcp.Client`** к **`http://localhost:8000/mcp`** (сервер должен быть запущен с `transport="http"`, как в `mcp.run(transport="http")` в этом же файле при прямом запуске). Один сценарий с фиксированным пользовательским сообщением и циклом обмена с моделью до финального ответа; **интерактивного** бесконечного ввода нет.
- Соответствие заданию: транспорт **HTTP** у клиента здесь ближе к формулировке курса; набор инструментов на сервере — учебный, не про `systemctl` напрямую.

### `client_ollama.py` (корень и `practic/`)

Тот же подход, что у корневого `client.py`, но LLM — **Ollama** (`http://localhost:11434/v1`). Полезно для локальной отладки без внешнего API.

### Тесты в `practic/`

- **`test_server.py`** — проверки логики `check_service_status` (мок `subprocess.run`).
- **`test_integration.py`** — интеграционные сценарии.

### Кратко: что куда смотреть

| Цель | Файлы |
|------|--------|
| Проверка сервиса через MCP tool `check_service_status` + диалог с пользователем и Gemini | `practic/server.py`, `practic/client.py` |
| MCP поверх HTTP + fastmcp Client | корневые `server.py` (с `transport="http"`) и `client.py` |
| Локальная модель | `client_ollama.py` |

Для **строгого** совпадения с критериями «в репозитории `server.py` и `client.py`» при сдаче обычно выкладывают в корень те версии, которые соответствуют чек-листу проверки; при необходимости их можно взять из `practic/` и поправить путь к Python / способ транспорта (HTTP vs stdio) под требования проверяющей системы.
